# 홈페이지 파티별 긴급 회의 결과

작성일: 2026-05-30  
대상: FamilySpace / 우리회사 홈페이지 운영  
작업 ID: homepage-party-meeting-20260530

## 회의 전 확인

직원들이 홈페이지를 봤는지에 대한 답은 "일부는 봤지만, 완료 기준으로 봐야 할 공개 홈페이지까지 제대로 본 것은 아니다"로 정리한다.

- 로컬 기준 주요 페이지와 내부 링크/이미지 감사는 이전 점검에서 통과했다.
- `https://tsst-csa.pages.dev/`는 HTTP 200으로 열리지만, 최신 `daily-meal-table` 및 `recipe-bulgogi-rice-paper-rolls` 반영은 확인되지 않았다.
- `https://test.tsst-csa.pages.dev/`는 404 상태다.
- `https://seyongjang2-sketch.github.io/tsst/`는 HTTP 200이지만 최신 변경 반영 기준 URL로 볼 수 없다.

따라서 지금까지의 문제는 "홈페이지를 전혀 보지 않았다"보다 더 심각하다. 봤다고 하더라도 로컬 화면, 일부 페이지, 일부 링크만 보고 공개 사이트 반영까지 확인하지 않은 상태에서 완료로 판단한 운영 실패다.

## 회의 결과

1. 결정된 사항

- 홈페이지 작업의 완료 기준은 로컬이 아니라 사용자가 실제로 보는 공개 URL이다.
- 공개 URL에서 최신 변경이 보이지 않으면 완료가 아니라 "배포 차단" 또는 "공개 반영 실패"로 보고한다.
- 각 파티 직원은 자기 영역만 보는 것이 아니라, 공개 URL에서 사용자 관점으로 최종 화면을 확인해야 한다.
- 앞으로 모든 홈페이지 작업은 수락 기준, 로컬 검증, 공개 URL 검증, 스크린샷 또는 확인 증거가 있어야 완료 처리한다.
- Cloudflare Pages를 운영 기준 후보로 두되, 연결 저장소/브랜치가 확정되기 전에는 운영 완료라고 말하지 않는다.

2. 해야 할 일

- 운영 총괄: 최종 공개 URL, 저장소, 브랜치를 하나로 확정한다.
- 웹 관리자: 반복 HTML, 네비게이션, 이미지 경로, 앵커 링크가 페이지별로 어긋나지 않게 관리한다.
- 콘텐츠 에디터: 사용자 요구가 화면에 직접 반영됐는지 확인한다. 레시피면 사진, 메뉴, 설명, 모바일 노출까지 본다.
- QA 리뷰어: 데스크톱/모바일, 내부 링크, 이미지, 공개 URL 반영 여부를 최종 확인한다.
- 배포 담당: Cloudflare test preview 404, GitHub Pages 구버전 노출, Cloudflare API/권한 차단을 정리한다.

3. 담당자

- 운영 총괄: 공개 운영 기준 확정 및 완료/보류 판단
- 웹 관리자: HTML/CSS/JS/이미지 수정과 구조 정리
- 콘텐츠 에디터: 페이지 목적과 실제 사용자 가치 검수
- QA 리뷰어: 화면/링크/이미지/모바일/공개 URL 검증
- 배포 담당: GitHub, Cloudflare Pages, 브랜치, 권한 문제 해결

4. 기한

- 즉시 적용: 완료 보고 기준 변경, 공개 URL 미반영 시 완료 금지
- 2026-05-30 안: 현재 공개 URL/브랜치/저장소 기준을 확정하거나, 확정 불가 사유를 별도 차단 이슈로 보고
- 다음 홈페이지 수정 전: 수락 기준 3~5개를 먼저 작성하고 작업 시작

5. 미해결 이슈

- Cloudflare Pages가 실제로 어느 저장소와 브랜치를 운영 기준으로 배포하는지 확정 필요
- `https://test.tsst-csa.pages.dev/` 404 원인 확인 필요
- GitHub Pages 구버전 노출을 폐기할지 최신화할지 결정 필요
- `CLOUDFLARE_API_TOKEN` 또는 wrangler login 권한이 없어 직접 배포 검증이 막힌 상태
- 현재 작업 트리에 `mom.html`, 레시피 이미지, 스크린샷, 감사 문서 변경이 남아 있어 커밋/배포 기준 정리가 필요

6. 다음 회의 전까지 확인할 것

- Cloudflare Pages 프로젝트의 연결 저장소와 브랜치
- 운영 기준 URL 하나
- 테스트 URL을 계속 쓸지 폐기할지
- 공개 URL에서 최신 `mom.html` 식단/레시피 사진이 보이는지
- 반복 HTML 구조를 공통 템플릿화할 범위

7. 다음 회의 전까지 공유할 자료

- `reports/homepage-management-audit-20260530.md`
- `agents/homepage_management_guidelines.md`
- `reports/homepage-party-meeting-20260530.md`
- 공개 URL 검증 결과
- 데스크톱/모바일 스크린샷 경로
- 배포 차단 또는 권한 요청 내역

8. 이후 진행 방향

- 홈페이지 운영은 "수정 -> 로컬 확인 -> 공개 URL 확인 -> 증거 기록 -> 완료 보고" 순서로만 진행한다.
- 공개 URL 확인이 막히면 개발 완료가 아니라 배포 차단으로 보고한다.
- 각 파티 직원은 자기 산출물의 존재만 확인하지 말고, 사용자가 그 페이지를 봤을 때 목적이 충족되는지까지 판단한다.
- 같은 문제가 반복되면 담당자 개인에게만 책임을 넘기지 않고, 체크리스트 미준수와 승인 체계 실패로 처리한다.

## 반성과 성찰

이번 문제의 핵심은 작업자들이 홈페이지를 "파일"로 봤지 "사용자가 보는 서비스"로 보지 못했다는 점이다. 로컬에서 보이는 것, 커밋된 것, 공개 URL에 반영된 것은 서로 다르다. 이 차이를 무시하면 사용자는 바뀌지 않은 홈페이지를 보고, 작업자는 완료했다고 착각한다.

또한 콘텐츠 파티는 사용자가 왜 그 페이지를 보는지 충분히 따지지 않았다. 레시피에 사진이 없거나, 가족 생활 페이지가 실제 행동을 돕지 못하면 기능상 오류가 없어도 실패다. QA 파티는 기술 통과만 볼 것이 아니라 사용자 요구 충족 여부를 확인해야 한다.

## 앞으로의 답

앞으로 홈페이지 운영의 답은 단순하다.

1. 최종 공개 URL을 하나로 고정한다.
2. 작업 전 수락 기준을 먼저 쓴다.
3. 로컬과 공개 URL을 둘 다 본다.
4. 공개 URL에서 안 보이면 완료라고 하지 않는다.
5. 스크린샷, 링크, 파일 경로를 남긴다.
6. 배포 권한이 없으면 즉시 차단으로 보고하고 승인 요청을 남긴다.

이 기준을 어기면 다음부터는 작업 실패가 아니라 운영 규칙 위반으로 기록한다.
